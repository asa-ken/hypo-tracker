# UI_REVIEW_LOOP.md

## 目的
Claude Codeが「UIを改善して」と言われたときだけでなく、対象画面を巡回して、観察→測定→改善→回帰を自律実行できるようにする。

## 0. 起点と対象選択
1. `docs/design/REVIEW_BACKLOG.md` を読む。
2. 最終レビュー日が古い、または状態が `要レビュー` の対象から次の1画面を選ぶ。
3. **観察は広く、実装は狭く。** 同一周で「実装する」テーマは1つだけ。ただし**観察・採点は必ず全次元に対して行う**。1テーマ制約がかかるのは Phase 3(仮説の選択)以降であって、Phase 1〜2(観察と問題の列挙)ではない。
4. 画面を変更する前に、既存テストと現在の実装を確認する。

> **この節を読み違えると自律ループが壊れる。**
> 「1周=1テーマ」を観察にまで適用すると、最初に見つけた問題で観察を打ち切る貪欲探索になる。
> 早くPRが出せて成果に見えるため、この誤りは自分では気づきにくい。
> 実際に2026-08-09のホームのレビューで発生し、`実運用摩擦=0` の欠陥を載せたまま完了扱いにした(`DECISIONS.md` 参照)。

## PRの単位

> **1周 = 1画面 = 1回の観察。そこから出た問題ごとに1PR。**

観察(Phase 0〜2)は画面ごとに1回にまとめる。ここが最も重い工程で、分割すると同じ測定を繰り返すことになる。
実装とPRは**問題ごとに分ける**。PRを分ける費用はほぼ無いのに対し、まとめたときに失うものが大きい。

### PRを問題ごとに分ける理由
PR履歴はこのプロジェクトで**一次資料として機能した実績がある**。
`BACKGROUND.md` のとおり、このデザイン規約自体、PR・コミット履歴から「何を変更したか」を、
会話履歴から「なぜ変更したか」を復元して作られた。将来の自分がそれを再びできる形で残す。

まとめたPRでは次が失われる。
- **本文の密度** — 問題・測定値・Self-Critiqueを1つの本文で分け合うことになり、各件の「問題→測定→検証」の鎖が切れる。コミットメッセージはこの密度を持てない。
- **索引** — 「到達経路の問題をいつ直したか」を探すとき、`ホーム: 3件の欠陥修正` は検索に引っかからない。人も将来のClaudeもPR一覧を走査する。
- **切り戻しの実用単位** — 後から実際にrevertするのはPRであってコミットではない。

### 分ける粒度
**1PR = スコアカードの1次元、または1つの明確な欠陥。** ファイル変更の単位ではない。

同じ次元の現れである複数の箇所は、1つのPRにまとめてよい。
例: 「空表現の文言不統一」と「ゼロ状態の案内欠落」は、どちらも `一貫性=1` の現れなので1PR。

PRの表題には、直した問題が分かる言葉を入れる。スコアカードの次元名を入れると、
後から**次元で横断検索**でき、画面をまたいだパターン(同じ構造の欠陥が他画面にもないか)が見える。

### 切り戻し可能性
各PRは**独立して切り戻せる**状態を保つ。
- 同じ関数に触れる複数のPRは、順に実装・マージして次を分岐させる。
- 別のPRに依存する場合は、その依存関係をPR本文に明記する。
- 独立させられない場合は、まとめて1PRにするか、事前に確認する。

### 確認の回数
確認が要るのは「**判断が必要なもの**」だけで、PRの数ではない。
`CLAUDE.md`「デザイン変更は事前確認ではなく事後の一括確認にする」に従い、
機能を改変しないデザイン変更は確認を挟まず連続して出し、1周の終わりにまとめて報告する。

## Phase 0 — Baseline
- ローカルサーバーを起動する。
- viewportは `390x844`。
- Playwrightで対象画面のスクリーンショットを撮り、`test/e2e/` 配下に保存する。既存の `closebtn.png` 等の前例に従う。
- 実データは `test/e2e/fixtures/testdata.json` を使用する。
- 変更前の `npm test` と `npm run e2e` を実行し、既存失敗を記録する。
- 「直す前に落ちることを確かめる」という既存E2Eルールを守る。

## ユーザーからの直接指摘への対応も、このループの対象である

`CLAUDE.md` は、ユーザーの明示的な指示は確認なしで即実装してよいと定めている。これはPhase 3(仮説選択)の
**確認**を省略してよいという意味であり、Phase 1(スコアカード)を省略してよいという意味ではない。
両者を混同し、「指示された内容を直接実装する」を繰り返した結果、`index.html` を4回連続で変更しながら
一度もPhase 1の11次元観察に戻らない、という省略が実際に発生した(`DECISIONS.md`
「取り込み画面で11次元チェックが機能しなかった原因」参照)。直接指摘への反応が続くほど、
「次はPhase 1に戻る」という判断そのものが自分の意思に委ねられ、機械的に検出できなかった。

これを踏まえ、次を必須にする。

- **`index.html` を変更するPRは、それが自律改善サイクルの成果であっても、ユーザー指摘への直接反応であっても、
  同じPRの中で `DECISIONS.md` に12次元そろったスコアカードを追加する。** 対象を「見た目に関わる変更かどうか」で
  絞らない。ロジックのみの修正に見えても対象とする(絞り込みを人手の判断に委ねると、また同じ形で省略が起きる)。
- 直近に同じ画面のスコアカードがある場合、12次元をゼロから再測定し直す必要はないが、
  **表そのものは毎回埋める**(変化のない次元は前回と同じ点・同じ根拠を転記してよい)。
- これは `test/e2e/scorecardgate.js` で機械的に検査する。`index.html` に差分があるのに
  `DECISIONS.md` の差分に12次元(認知負荷・情報構造・視覚的ノイズ・情報密度・Typography・Spacing・
  Hit Area・Color・Accessibility・一貫性・実運用摩擦・データ整合性)がすべて含まれていなければ失敗する。
  `npm run e2e` の一部として実行され、Stop Conditionsの「Phase 1のスコアカードが揃っていない」を
  人の記憶に頼らず検査する。データ整合性自体の欠陥検出は自動化していない(`DESIGN_SCORECARD.md` 参照)。
  このゲートが検査するのは「12次元の欄を埋めたか」という手続きの実施であって、各次元の中身の質ではない。

## Phase 1 — Observe(成果物: スコアカード)

**このPhaseの成果物はスコアカード表である。** 表を書き終えるまで Phase 2 へ進まない。
「見た」だけで通過させない。書けない次元があるなら、それは観察が足りていない。

対象画面を実データで表示し、`DESIGN_SCORECARD.md` の**12次元すべて**を0〜3で採点する。
各次元の測定方法は同文書の表が一次定義。書式は同文書の「記録テンプレート」に従う。

観察は**1つの状態だけで終わらせない**。最低でも次の3状態を見る。
- 実データが入った通常の状態(`test/e2e/fixtures/testdata.json`)
- 対象の情報が0件の状態(ゼロ状態・新規ユーザーが最初に見る画面)
- 対象の情報が多い状態(件数が増えたとき崩れないか)

見る観点(採点の入口。これ自体は成果物ではない):
1. 情報構造
2. 認知負荷
3. 操作摩擦
4. 視覚的重量
5. 一貫性
6. アクセシビリティ
7. 情報密度
8. 実運用上のコピペ・切替負荷

`DESIGN_PRINCIPLES.md` の原則と `DESIGN_SCORECARD.md` の評価次元を使う。

### 採点で機械的検査に頼ってよい範囲
`design.js` / `colortoken.js` / `escuse.js` / `sheettap.js` が見ている項目だけ、テスト結果を採点の根拠にできる。
どこまで見ているかは `DESIGN_SYSTEM.md` の「検査」欄が一次定義。
**検査の外にある次元(認知負荷・情報構造・一貫性・実運用摩擦など)を「テストが通ったから3点」と採点しない。**
これらは実画面・実データ・実操作で確かめる以外に方法がない。

## Phase 2 — Identify
Phase 1 の採点から、**1点以下がついた次元をすべて**問題として書き出す。
「見た目が好みでない」ではなく、観測可能な現象として記述する。
例:
- 境界線が多く、隣接情報の区切りが過剰に強い。
- 同じ操作なのに開閉UIが異なる。
- 重要情報と補助情報のコントラスト差が小さい。
- 同じ情報をコピーして別画面へ移す必要がある。

ここで列挙した問題のうち、**この周で直さないものは `REVIEW_BACKLOG.md` に残す。**
観察したのに記録しなければ、次の周からは存在しなかったことになる。

## Phase 3 — Hypothesize
Phase 2 で列挙した問題から、**`DESIGN_PRINCIPLES.md` 7の優先順位に従って1つだけ**選ぶ。
ここで初めて1テーマに絞る。0点がある場合は0点の次元から選ぶ。

1テーマにつき1つの改善仮説を立てる。
- Problem: 何が問題か
- Change: 何を変えるか
- Reason: なぜ改善すると考えるか
- Evidence: 何で確かめるか
- Risk: 何が悪化し得るか

以前撤回したパターンを `DECISIONS.md` で確認し、同じ失敗を再実装しない。

## Phase 4 — Implement
- `index.html` の編集は確認不要。UIは全て `index.html` にあるため、ここで止めるとループが成立しない。
- ただしトークン定義そのものの変更はユーザー確認が必要。
- `lib/` はCommonJSを維持する。
- 1仮説=1論理的変更単位にする。
- 新しい観点を機械的に検査できる場合、`test/e2e/` に1スイート追加する。1スイート=1観点。
- E2Eラベルは仕様として読める日本語にする。

## Phase 5 — Render
- ローカルサーバーを起動する。
- `test/e2e/fixtures/testdata.json` をlocalStorageへ流し込む。
- viewport `390x844` で対象画面を表示する。
- 変更前と同じ状態でスクリーンショットを取得する。

## Phase 6 — Inspect / Measure
### DOM
Playwrightで次を取得する。
- `getBoundingClientRect()` によるタップ領域
- `getComputedStyle()` による `font-size`, `gap`, `padding`, `margin`, `color`, `background-color`
- `#view.scrollHeight` によるスクロール量

padding / margin は測定はするが、トークン契約の対象ではない(`DESIGN_SYSTEM.md` 参照)。逸脱として一括修正しない。

### CSS
`index.html` のCSSを検索・正規表現集計し、font-size、gap等の使用種類を数える。新しい値がトークン外なら原因を確認する。

### Pixel
`test/e2e/png.js` を使い、スクリーンショットの画素を直接走査する。特に角丸、境界、背景色の残存など、目視だけでは決着できない問題に使う。
「見た目は画素で測る」を手続きとして扱う。

## Phase 7 — Regression
必ず両方を実行する。
1. `npm test`
2. `npm run e2e`

E2Eは `test/e2e/run_all.sh` の判定方式に従う。既存スイートを削除・弱体化して通すことは禁止する。

## Phase 8 — Compare(成果物: Before/After のスコアカード)
**Phase 1 と同じ12次元をもう一度採点し、Before/Afterを並べる。**
狙った次元だけを見ない。1テーマの変更が他の次元を下げていることがある。

- 問題が解消したか(狙った次元が上がったか)
- **他の次元が下がっていないか**(1点以上下がった次元があれば Phase 8.5 で必ず扱う)
- トークン逸脱がないか
- 実データで操作摩擦が増えていないか
- 0点の次元が残っていないか

## Phase 8.5 — Self-Critique
Compareのあと、必ず次を自問する。
- 情報を削っていないか。
- 操作を見つけにくくしていないか。
- 別画面との一貫性を壊していないか。
- 原因ではなく症状だけを直していないか。
- ルールを機械的に適用しすぎていないか。
- **Reversal Test: 変更前の方が良かった部分はないか。**

1つでも該当したらPhase 9へ戻す。撤回した場合は理由を `DECISIONS.md` に記録する。

この工程を省かない。自分の変更を肯定する方向にバイアスがかかるため、明示的に問わないと撤回の判断が出ない。過去に撤回した4件は、いずれも一度採用したあとに戻したものである。

## Phase 9 — Iterate
回帰が通り、改善が確認できたら、同一テーマ内で再評価する。
改善後に新しい問題が見つかった場合も、別テーマなら別周・別PRにする。

## Stop Conditions
次のいずれかで停止する。
- **Phase 1 のスコアカードが12次元そろっていない。**(そろうまで Phase 3 へ進まない)
- `npm test` または `npm run e2e` が失敗している。
- 1テーマ=1PRの境界を越える。
- トークン定義変更、情報アーキテクチャ変更、破壊的操作でユーザー確認が必要になった。
- 同じ画面で2周連続して、新しく見つかる問題が主観的なものだけになった。
- 測定結果が改善仮説を支持しない。
- 変更によって既存の機械的基準を破る。

## 完了扱いにできない条件
次のいずれかに当てはまる間、その画面を `REVIEW_BACKLOG.md` で `完了` にしない。
- **Phase 8 の再採点に0点の次元が1つでもある。**(`DESIGN_SCORECARD.md`「1つでも0がある場合は完了扱いにしない」)
- Phase 1 と Phase 8 のスコアカードが両方そろっていない。
- 実装した変更によって、他の次元が下がったまま説明されていない。

0点が残っている場合は、その画面を `要レビュー` のままにし、0点の内容を `REVIEW_BACKLOG.md` に書き出して次周へ送る。

## 完了時
- `REVIEW_BACKLOG.md` の最終レビュー日、直近の指摘、状態を更新する。
  状態を更新するときは、上の「完了扱いにできない条件」を必ず先に確認する。
- **この周で直さなかった1点以下の次元を `REVIEW_BACKLOG.md` に残す。**
- 採用・撤回の判断を `DECISIONS.md` に追記する。
- 1改善仮説=1論理的変更単位でcommitする。
- commit messageには「何を変えたか」だけでなく「どのUX問題を解決したか」が分かる文言を入れる。

### 1周の終わりの一括報告
デザイン変更は事前確認せずに進めるため、**1周の終わりの報告がユーザーの唯一の判断機会になる。**
次を必ず含める。

- **出したPRの一覧**。各PRについて「直した問題 / 変更内容 / 切り戻し単位」
- **12次元のスコアカード表(Before/After)**
- **最低の重要次元**
- 根拠となった測定結果、テスト結果
- **事前確認に回した項目**と、その理由
- 未解決事項

ユーザーはこの報告を見て個別に差し戻しを指示できる。差し戻しやすさが前提なので、
「まとめて1つにした方が説明しやすい」という理由でPRを束ねない。
