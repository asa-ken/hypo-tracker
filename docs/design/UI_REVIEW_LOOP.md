# UI_REVIEW_LOOP.md

## 目的
Claude Codeが「UIを改善して」と言われたときだけでなく、対象画面を巡回して、観察→測定→改善→回帰を自律実行できるようにする。

## 0. 起点と対象選択
1. `docs/design/REVIEW_BACKLOG.md` を読む。
2. 最終レビュー日が古い、または状態が `要レビュー` の対象から次の1画面を選ぶ。
3. **観察は広く、実装は狭く。** 同一周で「実装する」テーマは1つだけ。ただし**観察・採点は必ず全次元に対して行う**。1テーマ制約がかかるのは Phase 3(仮説の選択)以降であって、Phase 1〜2(観察と問題の列挙)ではない。
4. 画面を変更する前に、既存テストと現在の実装を確認する。

> **この節を読み違えると自律ループが壊れる。**
> 「1周=1テーマ」を観察にまで適用すると、最初に見つけた問題で観察を打ち切る貪欲探索になる。
> 早くPRが出せて成果に見えるため、この誤りは自分では気づきにくい。
> 実際に2026-08-09のホームのレビューで発生し、`実運用摩擦=0` の欠陥を載せたまま完了扱いにした(`DECISIONS.md` 参照)。

## PRの単位

> **1周 = 1画面 = 1回の観察。そこから出た問題ごとに1PR。**

観察(Phase 0〜2)は画面ごとに1回にまとめる。ここが最も重い工程で、分割すると同じ測定を繰り返すことになる。
実装とPRは**問題ごとに分ける**。PRを分ける費用はほぼ無いのに対し、まとめたときに失うものが大きい。

### PRを問題ごとに分ける理由
PR履歴はこのプロジェクトで**一次資料として機能した実績がある**。
`BACKGROUND.md` のとおり、このデザイン規約自体、PR・コミット履歴から「何を変更したか」を、
会話履歴から「なぜ変更したか」を復元して作られた。将来の自分がそれを再びできる形で残す。

まとめたPRでは次が失われる。
- **本文の密度** — 問題・測定値・Self-Critiqueを1つの本文で分け合うことになり、各件の「問題→測定→検証」の鎖が切れる。コミットメッセージはこの密度を持てない。
- **索引** — 「到達経路の問題をいつ直したか」を探すとき、`ホーム: 3件の欠陥修正` は検索に引っかからない。人も将来のClaudeもPR一覧を走査する。
- **切り戻しの実用単位** — 後から実際にrevertするのはPRであってコミットではない。

### 分ける粒度
**1PR = スコアカードの1次元、または1つの明確な欠陥。** ファイル変更の単位ではない。

同じ次元の現れである複数の箇所は、1つのPRにまとめてよい。
例: 「空表現の文言不統一」と「ゼロ状態の案内欠落」は、どちらも `一貫性=1` の現れなので1PR。

PRの表題には、直した問題が分かる言葉を入れる。スコアカードの次元名を入れると、
後から**次元で横断検索**でき、画面をまたいだパターン(同じ構造の欠陥が他画面にもないか)が見える。

### 切り戻し可能性
各PRは**独立して切り戻せる**状態を保つ。
- 同じ関数に触れる複数のPRは、順に実装・マージして次を分岐させる。
- 別のPRに依存する場合は、その依存関係をPR本文に明記する。
- 独立させられない場合は、まとめて1PRにするか、事前に確認する。

### 確認の回数
確認が要るのは「**判断が必要なもの**」だけで、PRの数ではない。
`CLAUDE.md`「デザイン変更は事前確認ではなく事後の一括確認にする」に従い、
機能を改変しないデザイン変更は確認を挟まず連続して出し、1周の終わりにまとめて報告する。

## Phase 0 — Baseline
- ローカルサーバーを起動する。
- viewportは `390x844`。
- Playwrightで対象画面のスクリーンショットを撮り、`test/e2e/` 配下に保存する。既存の `closebtn.png` 等の前例に従う。
- 実データは下記の2つのfixtureを使い分ける。
- 変更前の `npm test` と `npm run e2e` を実行し、既存失敗を記録する。
- 「直す前に落ちることを確かめる」という既存E2Eルールを守る。

### fixtureは2つある。観察には実運用規模の方を必ず通す

| fixture | 用途 |
|---|---|
| `test/e2e/fixtures/testdata.json` | 既存E2Eの基準データ。**回帰テストはこちらが正。** 小さく安定していることに価値がある |
| `test/e2e/fixtures/realdata.json` | 実運用規模のデータ。**Phase 1 の観察と Phase 8 の再採点は、必ずこちらも通す** |

`realdata.json` は、ユーザーが実際に貼った日東工器(6151)のデータ形状に合わせて作ってある。
`testdata.json` との違いは意図的なもので、次を含む。

- **業績推移20指標**(`testdata.json` は3)。表が縦に伸びる状態を作る
- **16文字の指標名**(「親会社株主に帰属する当期純利益」「営業活動によるキャッシュ・フロー」)。列幅と折り返しの崩れを作る
- **年度5列**。横スクロールの発生を作る
- **17セクションが埋まった銘柄**と、**1件も埋まっていない銘柄**を同居させる
- 1銘柄に注目ポイント5件・メモ3件・リマインダー3件が積み上がった状態

> **fixtureが綺麗すぎると、実運用でしか出ない崩れは永久に見つからない。**
> 2026-08-15に連続して出たユーザー報告(指標名の折り返しで数値列が隠れる、表が縦に伸びて
> グラフが画面外になる)は、どちらも `testdata.json` の3指標・短い名前では再現しない。
> 「多件数」の状態を、綺麗なfixtureを少し増やして作らないこと。実運用のデータ形状は、
> 件数だけでなく**名前の長さ・歯抜け・積み上がり方**が違う。

## ユーザーからの直接指摘への対応も、このループの対象である

`CLAUDE.md` は、ユーザーの明示的な指示は確認なしで即実装してよいと定めている。これはPhase 3(仮説選択)の
**確認**を省略してよいという意味であり、Phase 1(スコアカード)を省略してよいという意味ではない。
両者を混同し、「指示された内容を直接実装する」を繰り返した結果、`index.html` を4回連続で変更しながら
一度もPhase 1の11次元観察に戻らない、という省略が実際に発生した(`DECISIONS.md`
「取り込み画面で11次元チェックが機能しなかった原因」参照)。直接指摘への反応が続くほど、
「次はPhase 1に戻る」という判断そのものが自分の意思に委ねられ、機械的に検出できなかった。

これを踏まえ、次を必須にする。

- **`index.html` を変更するPRは、それが自律改善サイクルの成果であっても、ユーザー指摘への直接反応であっても、
  同じPRの中で `DECISIONS.md` に12次元そろったスコアカードを追加する。** 対象を「見た目に関わる変更かどうか」で
  絞らない。ロジックのみの修正に見えても対象とする(絞り込みを人手の判断に委ねると、また同じ形で省略が起きる)。
- 直近に同じ画面のスコアカードがある場合、12次元をゼロから再測定し直す必要はないが、
  **表そのものは毎回埋める**(変化のない次元は前回と同じ点・同じ根拠を転記してよい)。
- これは `test/e2e/scorecardgate.js` で機械的に検査する。`index.html` に差分があるのに
  `DECISIONS.md` の差分に12次元(認知負荷・情報構造・視覚的ノイズ・情報密度・Typography・Spacing・
  Hit Area・Color・Accessibility・一貫性・実運用摩擦・データ整合性)がすべて含まれていなければ失敗する。
  `npm run e2e` の一部として実行され、Stop Conditionsの「Phase 1のスコアカードが揃っていない」を
  人の記憶に頼らず検査する。データ整合性自体の欠陥検出は自動化していない(`DESIGN_SCORECARD.md` 参照)。
  このゲートが検査するのは「12次元の欄を埋めたか」という手続きの実施であって、各次元の中身の質ではない。

## Phase 1 — Observe(成果物: スコアカード)

**このPhaseの成果物はスコアカード表である。** 表を書き終えるまで Phase 2 へ進まない。
「見た」だけで通過させない。書けない次元があるなら、それは観察が足りていない。

対象画面を実データで表示し、`DESIGN_SCORECARD.md` の**12次元すべて**を0〜3で採点する。
各次元の測定方法は同文書の表が一次定義。書式は同文書の「記録テンプレート」に従う。

### 12次元は4パターンに分けて観察する(2026-08-10導入)

12次元を1回の観察でまとめて採点すると、分量の影響で根拠の厚さに偏りが出ることを実測で確認した
(最初と最後の次元だけ根拠が厚く、中間が薄くなるU字型。`DECISIONS.md`「スコアカード必須ゲート」
関連エントリ参照)。これを避けるため、12次元を次の4パターンに分けて観察する。

1. **機械測定群**: Typography・Spacing・Hit Area・Color・Accessibility・情報密度・視覚的ノイズ
2. **理解のしやすさ**: 認知負荷・情報構造
3. **整合性**: 一貫性・データ整合性
4. **運用コスト**: 実運用摩擦

パターン間はユーザー確認を挟まず連続して進めてよい(Phase 1は`CLAUDE.md`のどの確認ゲートにも
当たらない、副作用のない調査のため)。ただし**各パターンで必ず新しいツール呼び出し
(実測・grep・スクリーンショット比較・DOM比較・実操作等)を行う**こと。前回スコアの転記や
「テストがgreenだった」の一言だけで次のパターンへ進まない(パターン1の機械測定群は例外的に
既存テスト結果の参照でよいが、情報密度・視覚的ノイズだけは画面固有の実測が要る。下記
「採点で機械的検査に頼ってよい範囲」参照)。

観察の途中で、実際の使われ方など**実測できない事実**に判断が依存する場合は、そのパターンの
結論だけ保留し、推測で採点せずユーザーに確認する(例: 取り込み完了後の画面遷移が摩擦かどうかは、
1会話1銘柄か複数銘柄かという実利用パターンに依存し、確認して初めて判定できた)。

**この運用は導入したばかりで、効果はまだ検証中(n=1)。** 継続して精度が落ちていないか注意し、
問題があれば`DECISIONS.md`に撤回・修正の記録を残す。

### パターン②③は「仮説を1〜2件検証する」で終わらせず、機能グループを網羅する(2026-08-10改訂)

4パターン方式の1回目の実施で、ユーザー自身のチェックと突き合わせたところ、パターン②(理解のしやすさ)・
③(整合性)で実際に見落としが多数出た(`DECISIONS.md`同日エントリ参照)。原因は、「新しいツール呼び出しを
行う」ことは徹底したが、**その呼び出しの対象範囲を1〜2件の仮説検証で終えており、画面内の機能グループを
横断的に棚卸ししていなかった**こと。見つかった見落としのパターンは次の4種類。

- **意味的な重複の見落とし**(認知負荷): 文言が完全一致する繰り返しだけを検出し、文言は違うが同じ情報を
  別のUI要素が伝えている重複(例: 警告箱の「新しい指標が増えます」と、下の表の「新規」ラベル)を検出できなかった。
- **横断比較が1件で打ち切られた**(一貫性): 「メモ候補カード vs 個別銘柄カード」の1件だけ比較して満足し、
  同じ画面内の他の機能グループ(コピーボタン、トグルUI等)には同じ検証を広げなかった。
- **区分の内部に踏み込まなかった**(情報構造): 「直前PRで区分の再編成は整理済み」という結論に寄りかかり、
  区分の**内部**(サブグループ間の視覚的重みの差)を今回分として新規に観察し直さなかった。
- **個々の矛盾は検出したが集計値同士は見なかった**(データ整合性): 「分類ラベルと個別項目の矛盾」という
  具体的なバグパターンの再現テストだけに留まり、「画面の異なる場所に出る集計数値同士が整合しているか」
  という、より一般化した検証まで手を広げなかった。

これを踏まえ、パターン②③では次を追加で必須にする。

1. **観察前に、対象画面の機能グループを列挙する。** 例: コピー系ボタン、トグル系UI、カード系UI、
   数値・件数を表示している箇所、等。列挙リストを成果物として残す。
2. **列挙した機能グループごとに、画面内の他の使用箇所(または類似機能を持つ別画面)と横断比較する。**
   1件比較して「一貫性は概ね良好」と結論づけない。
3. **数値・件数を表示している箇所は、それぞれ何を数えているか(集計対象の定義)を明示的に書き出し、
   互いに一致すると期待されるものが実際に一致するか確認する。** 一致しない場合、それが「意味的に
   別のものを数えているため一致しなくてよい」のか「表示上紛らわしい」のかを判断する。
4. **区分・グルーピングの「外側」だけでなく「内側」も、既存PRで整理済みという理由で省略せず、その周ごとに
   観察し直す。**

### 12次元でカバーされない観点(2026-08-10追記)

一貫性次元は**アプリ内**の一貫性(同じ意味のUIが同じ方法で表現されるか)のみを見る。**アプリ外の一般的な
UI規約**(例: ON/OFFトグルは右側に置くのが一般的、等)との整合性は、12次元のどれにも属さない。
アプリ内に比較対象となる既存パターンが無い新規コンポーネントを作るときは、一貫性次元だけに頼らず、
一般的な規約との整合も観点として意識する。データ整合性を追加したときと同種の、次元設計の穴である
可能性がある(次元として独立させるべきかは、今後複数回この種の指摘が出るかを見てから判断する)。

観察は**1つの状態だけで終わらせない**。最低でも次の4状態を見る。
- 実データが入った通常の状態(`test/e2e/fixtures/testdata.json`)
- 対象の情報が0件の状態(ゼロ状態・新規ユーザーが最初に見る画面)
- 対象の情報が多い状態(`test/e2e/fixtures/realdata.json`。件数が増えたとき崩れないか)
- **同じ操作を2回続けた状態**(下記)

### 4つ目の状態: 「2回目」を必ず見る(2026-08-15導入)

**画面を開き、操作し、閉じて、もう一度開く。** この2回目にしか現れない欠陥がある。

- 前回の入力が残っている(「調べる項目を選ぶ」の深掘りテーマが、開き直しても前回の文字列を保持していた)
- 前回の選択が残っている / 逆に残ってほしいのに消えている
- 2回目だけ件数や状態表示がずれる(1回目の副作用が残っている)

1回目のスクリーンショットは正しく見える。**「初回の見た目」だけを観察対象にしている限り、この種の欠陥は構造上検出できない。**
実際、深掘りテーマの残留はレビューでは一度も挙がらず、ユーザーが2日にわたって使って報告した。

対象画面で「ユーザーが繰り返す操作」が何かを1つ決め、それを2回連続で実行して差分を見る。
繰り返す操作が無い画面(=一度きりしか使わない画面)なら、その旨をスコアカードに書いて省略してよい。

見る観点(採点の入口。これ自体は成果物ではない):
1. 情報構造
2. 認知負荷
3. 操作摩擦
4. 視覚的重量
5. 一貫性
6. アクセシビリティ
7. 情報密度
8. 実運用上のコピペ・切替負荷

`DESIGN_PRINCIPLES.md` の原則と `DESIGN_SCORECARD.md` の評価次元を使う。

### 採点で機械的検査に頼ってよい範囲
`design.js` / `colortoken.js` / `escuse.js` / `sheettap.js` / `component.js` / `visualnoise.js` / `shotmetrics.js`
が見ている項目だけ、テスト結果を採点の根拠にできる。
どこまで見ているかは `DESIGN_SYSTEM.md` の「検査」欄が一次定義。

後ろの3つは2026-08-22に追加したもので、視覚的ノイズと情報密度の**絶対量**を見る
(`component.js` はカード状コンテナの登録、`visualnoise.js` は線の本数、`shotmetrics.js` は
`ink` / `colored` / `scrollHeight`)。これらが通っていることは「その量が記録値から動いていない」
という意味であって、**その量が適切だという意味ではない**。適切かどうかは実画面で判断する。
**検査の外にある次元(認知負荷・情報構造・一貫性・実運用摩擦など)を「テストが通ったから3点」と採点しない。**
これらは実画面・実データ・実操作で確かめる以外に方法がない。

## Phase 1.5a — Traverse(成果物: 引っかかった瞬間の一覧)

**画面を見るのをやめて、仕事を最後まで通す。** Phase 1 が「1画面を1回見る」のに対し、
このPhaseは**ワークフローを端から端まで1回実行**し、受け渡しのたびに引っかかった箇所を記録する。

### なぜ必要か

このプロジェクトで実際に見つかった欠陥は、圧倒的に**画面と画面の継ぎ目**に集中している。

| 欠陥 | どこで見つかったか |
|---|---|
| 財務データが「その他」に落ちる | 外部AIの回答を実際に貼って取り込んだとき |
| 「銘柄またはテーマ:」が認識されない | アプリ自身が出した質問文の見出しを、そのまま貼り戻したとき |
| EPSと1株当たり純利益の表記ゆれ | 生成された説明書を読み、外部AIに渡した結果を見たとき |
| 深掘りテーマの残留 | 2回目に開いたとき |

いずれも**単一画面のスクリーンショットには写らない**。画面単位の観察を何周しても出てこない。

### 手順

対象画面が関わる中心ワークフローを1つ選び、途中で止めずに最後まで通す。銘柄なら例えば次。

1. 銘柄詳細を開く → 「会話を取り込む」へ
2. 説明書・質問文を実際にコピーする(**生成された文面を読む。** 中身を確認せずコピーしない)
3. その文面に沿った回答テキストを用意し、取り込みプレビューに貼る
4. プレビューの分類・警告・件数が、貼った内容と合っているか確認する
5. 取り込む → 銘柄詳細に戻り、入ったはずのデータが意図した場所に出ているか確認する
6. リマインダーを作り、発火時の文面まで確認する

### 記録するもの

スコアカードとは**別の成果物**として、次の形で書き出す。点数化しない。

```
- [どこで] 何を期待して / 実際に何が起きたか
例: [取り込みプレビュー] 財務実績を貼ったので指標に入ると思ったら、全部「その他・新規」になった
例: [調べる項目を選ぶ] 2回目に開いたとき、前回の深掘りテーマが入ったままだった
```

12次元は**状態を採点する**ものだが、ユーザーが報告してくるのは常に**期待とのズレた瞬間**である。
この2つは別物で、次元の点数からは瞬間が復元できない。だから別に記録する。

### 特に見る2種類の境界

1. **アプリの出力が、後でアプリの入力に戻る箇所。** 説明書・質問文・リマインダー設計プロンプトは
   外部AIを経由して `parseMd` / `parseReminder` に返ってくる。**出力側と入力側を別々に検査しても、
   往復は検査したことにならない。** EPS問題はこれで発生し、`promptsync.js` で塞いだ。
   新しく「アプリが文面を生成して外に出す」機能を作ったら、必ず往復を1回通す。
2. **画面をまたいで同じ情報を持ち回る箇所。** コピーして貼り直す、同じ内容を2回入力する、
   別画面に切り替えて確認する。回数を数えて記録する(実運用摩擦の一次根拠になる)。

## Phase 1.5b — Opportunity Lenses(成果物: 機会候補と、その審査結果)

**Phase 1〜1.5aは欠陥(期待とのズレ)を探す。ここは、何も壊れていなくても「もっと良くできる」を能動的に探す。**
2026-08-15、`DECISIONS.md`「発想を止める制約の棚卸し」で、既存の手順が欠陥駆動に偏っており、
新しい価値の提案を構造的に生まない(Evidence Hierarchyが未観測の便利さを却下する、
Negative Signalsの対になるものが無い、Hypothesizeのテンプレートが「問題」欄しか持たない等)ことが
判明し、この Phase を新設した。

**発見は必須、採用は任意。** 候補を出すことは毎周義務だが、実装するかどうかは下記「審査」で
厳密に判断する。**ほとんどの候補は見送りになってよい。** 見送りは失敗ではなく、正しい判定の一種。
この区別を崩すと、「やること」自体が目的化し、効果の薄い機能が積み上がる
(ユーザー指摘、2026-08-15:「実装は本当にそれが理にかなっているかは中立的に判断する」)。

### 手順(Phase 1.5 の通し実行に統合する。画面を分けない)

Phase 1.5a のワークフロー通し実行の中で、次の3つの固定レンズを毎回すべて適用する。
「思いつかなかった」で終わらせず、各レンズについて根拠(下記の情報源)を1つ以上あたる。
該当が無い場合も「無し」と、確認した情報源を明記して書く(0点を0点と書くのと同じ扱い)。

1. **記憶・再入力**: このアプリが既に持っているデータなのに、ユーザーに記憶・再入力させている箇所はないか
2. **反復**: 週に何度も繰り返している操作はないか
3. **手作業の残存**: 半年使い続けた人が「まだ手作業だ」と思う箇所はないか

各レンズで使う情報源(想像だけで書かない。毎回いずれか1つ以上を実際に調べる)。
- 会話履歴・`DECISIONS.md` の中の、ユーザー自身の発言を実際にgrepする(「毎回」「本当は」「手で」等)
- ログ・変更履歴データ(`log`, `changes` 等)から、操作の頻度を実際に数える
- 類似ツール(投資ノート・仮説管理系)を1つ調べ、このアプリに無い機能を1つ挙げる

**対象画面の外に波及する候補も拾ってよい(むしろ想定内)。** 画面ごとの通し実行の中で見つかった
候補が別画面に関わる場合、その画面名も記録する。

### 記録する場所
`REVIEW_BACKLOG.md` の「機会バックログ」に、対象画面の行と、画面横断の行の両方に記録する。
形式は次項の審査結果と合わせて1セットで書く。

### 審査(採用/見送りを判定する。ここが目的化を防ぐ歯止め)
見つけた候補ごとに、実装する前に次の4点を書く。0〜3のような点数ではなく、判断そのものを文章で書く。

```
- 候補: 何ができるようになるか
- 効果: 誰が・どのくらいの頻度で恩恵を受けるか(実データ・実利用頻度に基づく。推測のみで判定しない)
- コスト: 実装・データ構造・既存機能への影響・テストへの影響
- 代替: 既に近い手段が無いか(新しい入口を作らず既存の導線で足りないか)
- 判定: 採用候補 / 見送り(理由)
```

採用候補になったものだけが Phase 3 の仮説候補に進む。進んだ先で
`DESIGN_PRINCIPLES.md` 7の優先順位(既存の欠陥が上位)と競合する場合、欠陥を優先する。
情報アーキテクチャ・主要ワークフローに関わる採用候補は、`CLAUDE.md` の確認ゲートに従い、
実装前にユーザーへ確認する(欠陥修正と同じ扱い)。

## Phase 2 — Identify
Phase 1 の採点と Phase 1.5a の「引っかかった瞬間」の両方から、
**1点以下がついた次元と、記録した瞬間のすべて**を問題として書き出す。
「見た目が好みでない」ではなく、観測可能な現象として記述する。
例:
- 境界線が多く、隣接情報の区切りが過剰に強い。
- 同じ操作なのに開閉UIが異なる。
- 重要情報と補助情報のコントラスト差が小さい。
- 同じ情報をコピーして別画面へ移す必要がある。

ここで列挙した問題のうち、**この周で直さないものは `REVIEW_BACKLOG.md` に残す。**
観察したのに記録しなければ、次の周からは存在しなかったことになる。

## Phase 3 — Hypothesize
Phase 2 で列挙した問題から、**`DESIGN_PRINCIPLES.md` 7の優先順位に従って1つだけ**選ぶ。
ここで初めて1テーマに絞る。0点がある場合は0点の次元から選ぶ。

1テーマにつき1つの改善仮説を立てる。
- Problem: 何が問題か
- Change: 何を変えるか
- Reason: なぜ改善すると考えるか
- Evidence: 何で確かめるか
- Risk: 何が悪化し得るか

以前撤回したパターンを `DECISIONS.md` で確認する。**撤回した事実だけで恒久的に除外しない。**
撤回の理由を読み、その理由が今も成り立つかを判断する。前提条件が変わっていれば
(例: 依存していた機能が別PRで無くなった、既定値が変わった、データ規模が変わった)、
過去の撤回は現在の判断を拘束しない。理由が今も成り立つなら再実装しない。
「以前ダメだったから」だけを理由に候補から外すのは、`GRAPH_MAX`(存在自体を一度も
疑わなかった上限値、2026-08-15撤去)と同じ思考停止であり、これ自体が改善を妨げる制約になりうる
(`DECISIONS.md`「発想を止める制約の棚卸し」参照)。

## Phase 4 — Implement
- `index.html` の編集は確認不要。UIは全て `index.html` にあるため、ここで止めるとループが成立しない。
- ただしトークン定義そのものの変更はユーザー確認が必要。
- `lib/` はCommonJSを維持する。
- 1仮説=1論理的変更単位にする。
- 新しい観点を機械的に検査できる場合、`test/e2e/` に1スイート追加する。1スイート=1観点。
- E2Eラベルは仕様として読める日本語にする。

## Phase 5 — Render
- ローカルサーバーを起動する。
- `test/e2e/fixtures/testdata.json` をlocalStorageへ流し込む。
- viewport `390x844` で対象画面を表示する。
- 変更前と同じ状態でスクリーンショットを取得する。

## Phase 6 — Inspect / Measure
### DOM
Playwrightで次を取得する。
- `getBoundingClientRect()` によるタップ領域
- `getComputedStyle()` による `font-size`, `gap`, `padding`, `margin`, `color`, `background-color`
- `#view.scrollHeight` によるスクロール量

padding / margin は測定はするが、トークン契約の対象ではない(`DESIGN_SYSTEM.md` 参照)。逸脱として一括修正しない。

### CSS
`index.html` のCSSを検索・正規表現集計し、font-size、gap等の使用種類を数える。新しい値がトークン外なら原因を確認する。

### Pixel
`test/e2e/png.js` を使い、スクリーンショットの画素を直接走査する。特に角丸、境界、背景色の残存など、目視だけでは決着できない問題に使う。
「見た目は画素で測る」を手続きとして扱う。

## Phase 7 — Regression
必ず両方を実行する。
1. `npm test`
2. `npm run e2e`

E2Eは `test/e2e/run_all.sh` の判定方式に従う。既存スイートを削除・弱体化して通すことは禁止する。

## Phase 8 — Compare(成果物: Before/After のスコアカード)
**Phase 1 と同じ12次元をもう一度採点し、Before/Afterを並べる。**
狙った次元だけを見ない。1テーマの変更が他の次元を下げていることがある。

- 問題が解消したか(狙った次元が上がったか)
- **他の次元が下がっていないか**(1点以上下がった次元があれば Phase 8.5 で必ず扱う)
- トークン逸脱がないか
- 実データで操作摩擦が増えていないか
- 0点の次元が残っていないか

## Phase 8.5 — Self-Critique
Compareのあと、必ず次を自問する。
- 情報を削っていないか。
- 操作を見つけにくくしていないか。
- 別画面との一貫性を壊していないか。
- 原因ではなく症状だけを直していないか。
- ルールを機械的に適用しすぎていないか。
- **Reversal Test: 変更前の方が良かった部分はないか。**

1つでも該当したらPhase 9へ戻す。撤回した場合は理由を `DECISIONS.md` に記録する。

この工程を省かない。自分の変更を肯定する方向にバイアスがかかるため、明示的に問わないと撤回の判断が出ない。過去に撤回した4件は、いずれも一度採用したあとに戻したものである。

## Phase 9 — Iterate
回帰が通り、改善が確認できたら、同一テーマ内で再評価する。
改善後に新しい問題が見つかった場合も、別テーマなら別周・別PRにする。

## Stop Conditions
次のいずれかで停止する。
- **Phase 1 のスコアカードが12次元そろっていない。**(そろうまで Phase 3 へ進まない)
- **Phase 1.5a のワークフロー通し実行をしていない。**(スコアカードだけで Phase 3 へ進まない)
- **Phase 1.5b の3レンズを適用していない。**(候補が0件でも、レンズごとに確認した情報源を記録する)
- **`realdata.json` での観察をしていない。**(`testdata.json` だけで「多件数を見た」としない)
- `npm test` または `npm run e2e` が失敗している。
- 1テーマ=1PRの境界を越える。
- トークン定義変更、情報アーキテクチャ変更、破壊的操作でユーザー確認が必要になった。
- 同じ画面で2周連続して、新しく見つかる問題が主観的なものだけになった。
- 測定結果が改善仮説を支持しない。
- 変更によって既存の機械的基準を破る。

## 完了扱いにできない条件
次のいずれかに当てはまる間、その画面を `REVIEW_BACKLOG.md` で `完了` にしない。
- **Phase 8 の再採点に0点の次元が1つでもある。**(`DESIGN_SCORECARD.md`「1つでも0がある場合は完了扱いにしない」)
- Phase 1 と Phase 8 のスコアカードが両方そろっていない。
- **Phase 1.5a の「引っかかった瞬間」の一覧が無い。**(0件だった場合も「0件だった」と書く)
- **Phase 1.5b の機会候補と審査結果が無い。**(候補0件・採用0件でも、審査した記録として残す)
- **4状態(通常・ゼロ・多件数・2回目)のいずれかを見ていない。**
- 実装した変更によって、他の次元が下がったまま説明されていない。

0点が残っている場合は、その画面を `要レビュー` のままにし、0点の内容を `REVIEW_BACKLOG.md` に書き出して次周へ送る。

## 完了時
- `REVIEW_BACKLOG.md` の最終レビュー日、直近の指摘、状態を更新する。
  状態を更新するときは、上の「完了扱いにできない条件」を必ず先に確認する。
- **この周で直さなかった1点以下の次元を `REVIEW_BACKLOG.md` に残す。**
- 採用・撤回の判断を `DECISIONS.md` に追記する。
- 1改善仮説=1論理的変更単位でcommitする。
- commit messageには「何を変えたか」だけでなく「どのUX問題を解決したか」が分かる文言を入れる。

### 1周の終わりの一括報告
デザイン変更は事前確認せずに進めるため、**1周の終わりの報告がユーザーの唯一の判断機会になる。**
次を必ず含める。

- **出したPRの一覧**。各PRについて「直した問題 / 変更内容 / 切り戻し単位」
- **12次元のスコアカード表(Before/After)**
- **Phase 1.5a で引っかかった瞬間の一覧**(直したもの・送ったものを分けて)
- **Phase 1.5b の機会候補と審査結果**(採用したもの・見送ったものを理由とともに)
- **最低の重要次元**
- 根拠となった測定結果、テスト結果
- **事前確認に回した項目**と、その理由
- 未解決事項

ユーザーはこの報告を見て個別に差し戻しを指示できる。差し戻しやすさが前提なので、
「まとめて1つにした方が説明しやすい」という理由でPRを束ねない。
