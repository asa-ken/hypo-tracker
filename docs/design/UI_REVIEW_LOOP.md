# UI_REVIEW_LOOP.md

## 目的
Claude Codeが「UIを改善して」と言われたときだけでなく、対象画面を巡回して、観察→測定→改善→回帰を自律実行できるようにする。

## 0. 起点と対象選択
1. `docs/design/REVIEW_BACKLOG.md` を読む。
2. 最終レビュー日が古い、または状態が `要レビュー` の対象から次の1画面を選ぶ。
3. 同一周では1テーマだけ扱う。
4. 画面を変更する前に、既存テストと現在の実装を確認する。

## Phase 0 — Baseline
- ローカルサーバーを起動する。
- viewportは `390x844`。
- Playwrightで対象画面のスクリーンショットを撮り、`test/e2e/` 配下に保存する。既存の `closebtn.png` 等の前例に従う。
- 実データは `test/e2e/fixtures/testdata.json` を使用する。
- 変更前の `npm test` と `npm run e2e` を実行し、既存失敗を記録する。
- 「直す前に落ちることを確かめる」という既存E2Eルールを守る。

## Phase 1 — Observe
対象画面を実データで表示し、次を順に見る。
1. 情報構造
2. 認知負荷
3. 操作摩擦
4. 視覚的重量
5. 一貫性
6. アクセシビリティ
7. 情報密度
8. 実運用上のコピペ・切替負荷

`DESIGN_PRINCIPLES.md` の原則と `DESIGN_SCORECARD.md` の評価次元を使う。

## Phase 2 — Identify
問題を「見た目が好みでない」ではなく、観測可能な現象として記述する。
例:
- 境界線が多く、隣接情報の区切りが過剰に強い。
- 同じ操作なのに開閉UIが異なる。
- 重要情報と補助情報のコントラスト差が小さい。
- 同じ情報をコピーして別画面へ移す必要がある。

## Phase 3 — Hypothesize
1テーマにつき1つの改善仮説を立てる。
- Problem: 何が問題か
- Change: 何を変えるか
- Reason: なぜ改善すると考えるか
- Evidence: 何で確かめるか
- Risk: 何が悪化し得るか

以前撤回したパターンを `DECISIONS.md` で確認し、同じ失敗を再実装しない。

## Phase 4 — Implement
- `index.html` の編集は確認不要。UIは全て `index.html` にあるため、ここで止めるとループが成立しない。
- ただしトークン定義そのものの変更はユーザー確認が必要。
- `lib/` はCommonJSを維持する。
- 1仮説=1論理的変更単位にする。
- 新しい観点を機械的に検査できる場合、`test/e2e/` に1スイート追加する。1スイート=1観点。
- E2Eラベルは仕様として読める日本語にする。

## Phase 5 — Render
- ローカルサーバーを起動する。
- `test/e2e/fixtures/testdata.json` をlocalStorageへ流し込む。
- viewport `390x844` で対象画面を表示する。
- 変更前と同じ状態でスクリーンショットを取得する。

## Phase 6 — Inspect / Measure
### DOM
Playwrightで次を取得する。
- `getBoundingClientRect()` によるタップ領域
- `getComputedStyle()` による `font-size`, `gap`, `padding`, `margin`, `color`, `background-color`
- `#view.scrollHeight` によるスクロール量

padding / margin は測定はするが、トークン契約の対象ではない(`DESIGN_SYSTEM.md` 参照)。逸脱として一括修正しない。

### CSS
`index.html` のCSSを検索・正規表現集計し、font-size、gap等の使用種類を数える。新しい値がトークン外なら原因を確認する。

### Pixel
`test/e2e/png.js` を使い、スクリーンショットの画素を直接走査する。特に角丸、境界、背景色の残存など、目視だけでは決着できない問題に使う。
「見た目は画素で測る」を手続きとして扱う。

## Phase 7 — Regression
必ず両方を実行する。
1. `npm test`
2. `npm run e2e`

E2Eは `test/e2e/run_all.sh` の判定方式に従う。既存スイートを削除・弱体化して通すことは禁止する。

## Phase 8 — Compare
Baselineと変更後を比較する。
- 問題が解消したか
- 新しい問題が発生していないか
- Scorecardの重要次元が悪化していないか
- トークン逸脱がないか
- 実データで操作摩擦が増えていないか

## Phase 8.5 — Self-Critique
Compareのあと、必ず次を自問する。
- 情報を削っていないか。
- 操作を見つけにくくしていないか。
- 別画面との一貫性を壊していないか。
- 原因ではなく症状だけを直していないか。
- ルールを機械的に適用しすぎていないか。
- **Reversal Test: 変更前の方が良かった部分はないか。**

1つでも該当したらPhase 9へ戻す。撤回した場合は理由を `DECISIONS.md` に記録する。

この工程を省かない。自分の変更を肯定する方向にバイアスがかかるため、明示的に問わないと撤回の判断が出ない。過去に撤回した4件は、いずれも一度採用したあとに戻したものである。

## Phase 9 — Iterate
回帰が通り、改善が確認できたら、同一テーマ内で再評価する。
改善後に新しい問題が見つかった場合も、別テーマなら別周・別PRにする。

## Stop Conditions
次のいずれかで停止する。
- `npm test` または `npm run e2e` が失敗している。
- 1テーマ=1PRの境界を越える。
- トークン定義変更、情報アーキテクチャ変更、破壊的操作でユーザー確認が必要になった。
- 同じ画面で2周連続して、新しく見つかる問題が主観的なものだけになった。
- 測定結果が改善仮説を支持しない。
- 変更によって既存の機械的基準を破る。

## 完了時
- `REVIEW_BACKLOG.md` の最終レビュー日、直近の指摘、状態を更新する。
- 採用・撤回の判断を `DECISIONS.md` に追記する。
- 1改善仮説=1論理的変更単位でcommitする。
- commit messageには「何を変えたか」だけでなく「どのUX問題を解決したか」が分かる文言を入れる。
- 変更内容、根拠、測定結果、テスト結果、未解決事項をユーザーに報告する。
