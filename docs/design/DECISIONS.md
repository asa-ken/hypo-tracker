追記型の意思決定ログ。既存判断を再検討するときも過去エントリを削除・上書きせず、新しいエントリを追加する。

## エントリ形式
- **Date:** YYYY-MM-DD
- **Problem:** 問題
- **Decision:** 採用した判断
- **Reason:** 判断理由
- **Evidence:** 実測、ユーザー行動、テスト、画素測定等
- **Status:** 採用 | 撤回

### 2026-08-09 — ホーム「対応が必要」を廃止し、期限切れ/今日のリマインダー/リマインド未登録/今週の予定の4区分に再構成

### 2026-08-09 — ホームの並べ替え(空の区分を下に送る)を撤回

- **Evidence:** 使い捨てブランチで3パターンを検証した。(1) `index.html` のみ変更・スコアカードなし → 修正前と同じく `❌`(12次元すべて `missing` として列挙)。(2) 12次元の名前はあるが点・根拠が空欄の行 → **修正前は `✅`(誤って通過)だったが、修正後は `❌`(12次元すべて `missing` として列挙)** になることを確認。(3) 12次元の名前・点・根拠がすべて埋まった行(過去の実例に基づく複数の書式: 単純な `| 名前 | 点 | 根拠 |`、太字の `| **名前** | **点** | ... |`、Before/After 2列の `| 名前 | Before | After | 根拠 | 新規/既存 |`)→ いずれも `✅`。検証後、使い捨てブランチは破棄した。`npm test` 121件・`npm run e2e` 全64スイートgreen。
- **Self-Critique:**
  - これで抜け穴は完全に塞がったか → いいえ。点・根拠のセルに**実在する値**があることは強制できるが、その値が**実際に画面を観察して得た正しい値か**(例: 適当に「3」と書いて「実データ確認」とだけ書く)は機械検査できない。この限界は `DESIGN_SCORECARD.md` にも明記済みで、質の担保はPhase 8.5の自己批判・ユーザーレビューに委ねる方針を維持する。
  - 「一部の次元だけ本気で採点し、残りは適当に埋める」という部分的な手抜きは防げるか → 防げない。今回のゲートは「12次元すべてに何かしらの点・根拠が存在するか」という形式検査であり、次元ごとの採点の妥当性(質)は検査対象外。これは意図的な設計上の境界であり、ユーザーへの回答でもその旨を明示する。
