# DESIGN_SCORECARD.md

## 目的
UI改善を「平均点」ではなく、重要な弱点を見つけるために評価する。
**平均点は出さない。最も低い重要次元を総合判定として採る。**

## この採点はいつ行うか
`UI_REVIEW_LOOP.md` の **Phase 1 の成果物**であり、**Phase 8 で再採点**する。どちらも省略できない。
採点表が無い状態で Phase 3(仮説の選択)へ進まない。

**自律改善サイクル(Phase 0〜9)の成果物としてだけでなく、ユーザー指摘への直接反応で `index.html` を
変更するときも同様に必須。**「確認なしで即実装してよい」(`CLAUDE.md`)は Phase 3 の確認を省いてよいという
意味であり、この採点を省いてよいという意味ではない。省略すると `UI_REVIEW_LOOP.md`
「ユーザーからの直接指摘への対応も、このループの対象である」に書いた通りの再発が起きる。
`test/e2e/scorecardgate.js` が、`index.html` の変更に対して `DECISIONS.md` へ12次元そろった
採点が追加されているかを機械的に検査する(`npm run e2e` の一部)。

**採点は「見た」ことの記録ではなく、書き出す表そのものが成果物である。**
12次元すべてに点と根拠を書けない場合、それは観察が足りていないという意味であって、
「該当なし」でも「省略可」でもない。

**採点の進め方(実行順)は `UI_REVIEW_LOOP.md` Phase 1「12次元は4パターンに分けて観察する」が一次定義。**
12次元を1回でまとめて採点すると分量の影響で根拠が薄くなる次元が出ることを実測で確認したため、
機械測定群/理解のしやすさ/整合性/運用コストの4パターンに分けて観察する。

## 評価方法
各次元を 0〜3 で評価する。
- 3: 問題なし
- 2: 軽微な問題
- 1: 明確な問題
- 0: 重大な問題

数値は比較・発見のための観測値であり、点数を上げること自体を目的にしない。1つでも0がある場合は完了扱いにしない。重要次元で1以下が残る場合は、他の次元を改善して平均を上げるのではなく、その弱点を優先する。

### 点の付け方の基準
- **0** … その次元の目的が達成できていない。操作不能、到達不能、WCAG不合格、情報が失われている等。
- **1** … 実データで再現でき、言葉で説明できる欠陥がある。
- **2** … 欠陥と言うほどではないが、より良い形が具体的に指摘できる。
- **3** … 現時点で指摘が出ない。**「測っていない」を3にしない。**

### 既存の欠陥と、今回作った欠陥を区別する
低い点をつけたとき、それが**この周の変更で生じたのか、以前から存在したのか**を必ず併記する。
区別しないと、他人の家事を自分の失点として直し続けるか、逆に自分の失点を「元からあった」で流すことになる。
判定には `git show <変更前のcommit>:index.html` で変更前の実装を確認する。

## 評価次元と測定方法

| 次元 | 観測内容 | このリポジトリでの測定 |
|---|---|---|
| 認知負荷 | 重要情報と補助情報の区別、重複、義務感 | 実データ画面を目視し、同じ意味の表示・不要な状態強調・操作要求を列挙 |
| 情報構造 | グルーピング、階層、開閉の一貫性 | 対象画面のDOM構造と実画面を比較。見出し・余白・開閉関係を確認 |
| 視覚的ノイズ | 線、枠、色、バッジ、矢印等の過剰使用 | **線の絶対量**: `test/e2e/visualnoise.js` が主要画面の線(border)の本数を実レンダリングから数え、記録値と一致するかを見る。**面積の絶対量**: `test/e2e/shotmetrics.js` が `#view` の画素から `ink`(地色以外の割合)と `colored`(有彩色の割合)を測る。**差分**: スクリーンショットを比較し、装飾要素の追加・削除を確認。色残存はPNG画素測定 |
| 情報密度 | 必要情報を保ったまま画面を圧迫していないか | `#view` の `scrollHeight` をPlaywrightで取得し、変更前後を比較。`test/e2e/shotmetrics.js` が主要画面の `scrollHeight` を記録値と照合する(差分だけでなく絶対量も見る) |
| Typography | 文字サイズの階層と過小文字 | `index.html` のCSSを正規表現で集計し、`11/12/13/15/17px` と入力欄16px以外を検出。11px は許容、11px未満が違反 |
| Spacing | 余白の一貫性 | `index.html` の **`gap` のみ**を集計し、4/8/12/16px以外の新規値を検出。padding / margin はトークン化されていないため対象外(`DESIGN_SYSTEM.md` 参照) |
| Hit Area | タップ可能領域 | `design.js`(主要4画面)と `sheettap.js`(各シート)が `getBoundingClientRect()` で44px未満を検出。新しいシートを足したら `sheettap.js` に追加する |
| Color | トークン逸脱・局所的な残色 | `colortoken.js` がトークン17個と直書きの増加を検出。角丸等の残色は `test/e2e/png.js` の画素スキャンで測定 |
| Accessibility | タップ、コントラスト、入力操作等 | DOMの実寸、実機想定390x844、既存E2Eを使用。重大な操作不能は0点 |
| 一貫性 | 同じ意味のUIが同じ方法で表現されるか | 同一機能を画面横断で比較し、開閉・状態・操作領域を列挙 |
| 実運用摩擦 | コピペ、画面切替、冗長入力 | 実データで中心ワークフローを一連で操作し、同じ情報を手作業で移す回数を記録 |
| データ整合性 | 表示文言・ラベル・分類が、実データや検出結果と論理的に矛盾しないか | 複数の検出結果パターンが**同時に**混在するデータ(例: 近い既存指標が見つかったものと見つからなかったものが同一画面に同時に存在する)を実際に貼り付け、各行・各ボックスの文言が対応するデータと食い違わないかを目視で確認する。単一パターンのみのテストデータでは再現しないため、組み合わせを意識してテストデータを作る |

**データ整合性は他の11次元と性質が異なる。** 視覚・構造・操作性ではなく、表示内容とロジック/データの一致を見る次元であり、
2026-08-10の「受注残高」問題(近い既存指標が見つからなかった新規指標に対し、見つかった指標と同じボックスの
「似た指標があります」という文言が付いてしまった)で顕在化した。他の次元と異なり、機械的な自動検出は持たない
(`DECISIONS.md` 参照。個々の不整合パターンは無数にあり、汎用的な静的検査で網羅するのは非現実的なため、
観察方法の明文化のみで対応する)。**組み合わせを意識したテストデータを使わない限り再現しない**ことが多いため、
Phase 1・Phase 8で「多件数」の状態を作るときは、単一パターンの繰り返しではなく、異なる検出結果パターンを
意図的に混在させる。実運用規模のfixture `test/e2e/fixtures/realdata.json` は、この混在
(データが揃った銘柄・歯抜けの銘柄・空の銘柄の同居)を含めて作ってある。

## 機械的な基準
- タップ領域: 44px未満を許容しない。
- 文字サイズ: 11px未満を許容しない。定義済み6種類以内。
- gap: `4/8/12/16px` の4段階以外を新規導入しない。
- 指標グリッド: 2列。
- デザイン契約: `design.js` / `colortoken.js` / `escuse.js` / `sheettap.js` / `component.js` / `visualnoise.js` / `shotmetrics.js` の検査に合格する。
- 線の量: 主要画面の線の本数を増やさない(`visualnoise.js`)。増減させたときは理由を `DECISIONS.md` に書き、記録値を更新する。
- 面積と高さ: 主要画面の `ink` / `colored` / `scrollHeight` を記録値から動かさない(`shotmetrics.js`)。同上。
- コンポーネント: カード状のコンテナを未登録のまま増やさない(`component.js`)。
- 回帰: `npm test` と `npm run e2e` の両方に合格する。

### 差分だけを見る指標は、蓄積する劣化を検出できない
「視覚的ノイズ」は長らく**その周の追加・削除**だけを見ていた。各周で新しい枠線を足していないので
毎回3点が付き続け、一方で線の絶対量は周をまたいで蓄積していた。ユーザー指摘
(「取り込む画面全般的に枠線やエリアの境界線が多くてビジー感があります」)まで気づけなかった。
2026-08-22に絶対量の測定(線の本数は `visualnoise.js`、面積と高さは `shotmetrics.js`)を足してこの穴を塞いだ。
線と面積は別々に測る必要がある。実測で、**色だけを変えて線を1本も動かさない変更**(警告カードの地色を
amberに戻す)は `visualnoise.js` を素通りし(41本のまま)、`shotmetrics.js` だけが捉えた
(`colored` 10.05% → 26.55%)。逆に枠線の復活は線の本数に出る(41→57本)。
**他の次元にも同じ形の穴がないか**を、次元を追加・変更するときに確認する。

## Negative Signals
以下は改善テーマとして優先的に調査する。
- 同じ情報の重複表示
- 「要更新」「不足」等による過剰な義務感
- 同じ意味を異なるUIで表す箇所
- 装飾要素がコンテンツより強い箇所
- 44px未満の操作領域
- 11px未満の文字
- gap tokenからの逸脱
- 画素で確認できる残色・境界不良
- コピペ・画面切替・再入力の反復
- 実データ投入時だけ発生する崩れ
- 文言が一部のデータにしか当てはまらないのに、全件・全状態に同じ文言が付いている

対応済みの意思決定は `DECISIONS.md` に記録する。「仮説」→「注目ポイント」は対応済みの決定だが、
**決定した理由が今も成り立つ前提でのみ**再提案の対象外とする。前提が変わっていれば
(命名の背景にした利用実態が変わった等)、再検討してよい(`DECISIONS.md`「発想を止める制約の棚卸し」参照)。

## Opportunity Signals
Negative Signals は「壊れている・崩れている」を探すためのものだが、こちらは**壊れていなくても
価値を足せる**箇所を探すためのもの。`UI_REVIEW_LOOP.md` Phase 1.5b の3レンズで使う。
- アプリが既に持っているデータを、ユーザーが記憶・再入力させられている
- 同じ操作を高頻度で繰り返している(実データ・ログで頻度が確認できる)
- 半年使い続けた前提で見ると、まだ手作業が残っている
- 類似ツールには当たり前にある機能が、このアプリには無い

Negative Signals と違い、**これらは「今すぐ直すべき欠陥」ではない。** 見つけても実装するとは限らない。
採用するかどうかは `UI_REVIEW_LOOP.md` Phase 1.5b の「審査」で、効果・コスト・代替手段を
中立に比較して判断する。**発見自体を目的化しない**(候補を出すことは義務だが、実装することは義務ではない)。

## Evidence Hierarchy
UI判断の根拠は次の順に強い。上位が下位と矛盾する場合は上位を採る。

1. ユーザーの実利用フィードバック
2. 実データでの実操作
3. 実画面のレンダリング結果・スクリーンショット
4. 画素・DOMの測定値
5. E2E / ユニットテストの結果
6. コード読解
7. 既存のプロジェクト慣習
8. 一般的なデザイン論・美的判断

8だけを根拠にUIを変更しない。「こちらの方が美しい」は、情報階層・可読性・認知負荷・一貫性のいずれかに翻訳できて初めて根拠になる。

**例外: Opportunity Signals(上記)の候補は、12次元のどれかへの翻訳を必須としない。**
「まだ誰も困っていないが、明らかに便利になる」という提案は、既存の欠陥次元に翻訳しようとすると
無理に欠陥をでっち上げることになる。かわりに `UI_REVIEW_LOOP.md` Phase 1.5b の「審査」
(効果・コスト・代替)で判断する。この例外は Opportunity Signals 由来の候補だけに適用し、
それ以外の「美しさ」だけを根拠にした変更にまで広げない。

3が4より上位なのは実績に基づく。角丸クリップの残色では、CSS契約テスト(5)と目視が「解決した」と誤判定し、画素測定(4)で初めて残存が判明した。逆に測定値が良くても実画面で破綻していれば、実画面を採る。

## 判定
最終報告には、各次元の点数、最低の重要次元、機械的検査結果、未解決事項を示す。平均点は出さない。

## この採点が守れているかの確認
機械的検査(`design.js` 等)は**この採点そのものを検査しない。**
`npm test` と `npm run e2e` が全部通っていても、スコアカードを書かなかったことは検出されない。
したがってテストの成功は、この手順を踏んだ証拠にならない。踏んだかどうかは提出物の有無で判断する。
